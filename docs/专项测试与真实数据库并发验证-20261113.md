## 后续整改：F01 库存交付与 F02 充值幂等

用户随后授权修复这两项重要问题。F01、F02 已按下述规则整改；本节记录修复后的结果，后文为整改前的验证快照。

- **F01：付款前预留库存。** 实物库存仍在发药时扣减；已付款未发药处方的数量作为预留量。付款持有现有管理员、患者、预约/处方和药品行锁，使用锁定当前读检查 `实物库存－已付款预留量`，不足时拒绝收款。付款、流水、处方/预约状态和通知处于同一事务。发药扣实物库存并转为 dispensed 后，预留随状态释放。管理端不能将库存降到已预留数量以下，两个停用入口均拒绝停用仍有待取药处方的药品；删除继续受处方引用保护。
- **F02：稳定请求标识与成功结果分离。** 充值接口和服务层均要求非空幂等键，不再接受无键充值。客户端按患者、金额和渠道保存待确认操作；不确定的请求重试复用原键，服务端明确成功后新的主动充值使用新键。充值成功后的余额刷新失败单独提示，不再误报充值失败。
- 待确认操作不设自动过期；即使隔天重进也不能擅自换键。新键必须先持久化并回读确认，存储读取、写入或静默写入失败时均不提交充值。成功后清理失败会保留成功标记，使新充值能够换键；若成功标记也未能写入且页面被重建，只安全确认旧操作，并提示“上次充值已确认”。
- 无需修改表结构，也没有在业务库调整处方、余额或库存。只读检查当前业务库的已付款处方，发现库存不足/停用药品和异常明细的计数均为 0；不据此声称实现了历史药费退款功能。

- 仅通过 `CREATE TABLE ... LIKE` 复制 16 张表的结构，复制业务记录数为 0；患者、员工、药品和订单均为合成数据。库内另有验证守卫、故障开关和专用触发器。
- 12 线程场景在各自事务内取得 12 个不同 MySQL 连接，再经屏障同时放行；双向竞争场景核对 2 个不同连接。抢最后号源、同患者建单、同键充值、同单付款、付款/取消、过期回收/付款、同处方发药等核心场景重复 3 轮；其他场景为单轮，不将全部用例描述为三轮压测。
- Redis 使用隔离内存替身，未接入正在运行的 Redis。小程序使用真实 Page/App/请求模块，替换 wx/API 边界；没有新发起真实微信登录或外部支付。

F01 使用真实开方、并发付款和并发发药链路，观察值如下：

```text
payments=2,dispensed=1,strandedPaid=1,stock=0
netDebit=20.00,deliveredAmount=10.00,balances=90.00/90.00
```

这表示模拟余额账本合计扣款 20 元，只交付 10 元药品，仍有一笔已收款未交付且无退款的处方。用例允许在开方或付款时合理拒绝缺货请求，不强制未来修复仍必须接受两笔付款。

四类 SQL 故障均由**测试库专属触发器**使用 `SIGNAL SQLSTATE '45000'` 注入；用例核对准确 SQLState 与对应消息，再检查事务后的持久化状态，结果全部通过：

1. 扣余额后的支付流水写入失败：余额、订单、流水和消息均回滚。
2. 退款流水写入失败：取消、退款和号源变更回滚。
3. 扣库存后的处方状态写入失败：库存、处方和预约状态回滚。
4. 占号建单后的通知写入失败：订单与占号回滚。

并发结论适用于当前生产代码保留的全局管理员行锁及其他既有锁路径；不能推断移除该全局锁后的正确性，也没有测吞吐、延迟或长时间稳定性。

