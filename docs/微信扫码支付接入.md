# 微信 Native 扫码支付接入与验证

当前副本已接入参考项目所用商户的 API v2 Native 扫码支付。参考商户参数通过微信官方签名查单、下单和关单验证；没有执行真实付款。微信登录继续使用当前小程序账号，扫码通道使用独立商户 AppID，二者无需混为一套配置。

2026-11-14 更新：用户已确认微信真实充值成功；本项目恢复“支付宝（模拟）”作为对照，挂号、药费和充值页面均可选择。下文自动化测试“不执行真实付款”描述的是工具验收范围，不否认用户随后完成的实付。

## 使用方式

1. 在当前项目根目录运行一键启动脚本。后端固定为 `127.0.0.1:18080`，电脑前端固定为 `127.0.0.1:15173`。
2. 微信开发者工具重新编译小程序，登录后在挂号、订单、处方或充值中选择微信支付。
3. 小程序进入扫码页。在电脑开发者工具里显示二维码时，可直接用手机微信扫一扫；在手机上打开小程序时，可复制电脑收银台链接，在运行项目的电脑浏览器打开，再用手机扫码。
4. 核对金额后在手机微信确认。Native 二维码需用微信扫一扫，不能依靠长按或相册识别。系统查单确认后才显示支付成功、增加余额或推进订单状态。
5. 不付款时可点击关闭支付。普通返回不会把未知结果当成失败，支付单仍保留；后台会继续查单，防止重试重复结算。

**这是会真实扣款的扫码通道，收款方属于参考项目所配置的商户。学习验收可先主动输入 0.01 元充值，扫码前核对手机微信显示的收款方和金额。本次自动验证没有展示可付款二维码，也没有替用户确认付款。**

2026-11-14 最近一次重启检测到局域网地址为 `192.168.0.46`，启动器已更新小程序 `network-config.js`。手机与电脑仍须在同一局域网，重新编译后生效；电脑收银台链接使用 `127.0.0.1:15173`，应在运行本项目的电脑上打开。

## 代码与配置

- 商户配置仅保存在被版本忽略的 `.local/wechat-pay.properties`。参考项目未修改，原三端工程未修改，不在源码保存商户 API 密钥。
- 后端实现位于 `backend/src/main/java/com/aaa/aihealthcare/payment/`；接口位于 `NativePaymentController`。
- 小程序统一入口为 `utils/native-pay.js` 和 `pages/payment/native`；电脑页为 `admin-web/src/views/NativeCashierPage.vue`，公开路由 `/cashier/:token`。
- 数据库仅在当前副本增量创建 `wechat_native_payment`。原 16 张业务表结构保持原状，支付单以业务类型关联预约、处方或充值。
- `healthcare.payment.wechat-native.enabled=true` 时，微信一律走真实扫码，旧接口拒绝微信模拟入账；支付宝保留为“支付宝（模拟）”，走原教学模拟流程；余额支付保留。配置读取失败时不把微信降级成模拟付款。

当前没有公网 HTTPS 回调域名，教学环境通过主动查单确认结果，后台每 15 秒补查，页面查询至少相隔 3 秒。通知处理代码已实现并验签，但不能把当前内网 notify_url 描述为公网回调已送达；后续有公网地址后可配置为真实回调入口。

## 交易与资源保护

创建 Native 支付单只申请二维码，不等于业务到账。只有经过验签、商户核对、商户订单号与金额核对的微信成功结果，才在本地事务中写支付流水和推进业务状态。充值键、商户订单号、微信交易号及活动支付单有持久化唯一约束，重复查单或通知不会重复入账。

真实扫码不扣应用余额。挂号扫码成功写真实渠道流水；药费扫码成功将处方转 paid；充值扫码成功才增加余额。老接口只允许余额和支付宝模拟，真实微信请求必须走扫码入口。支付宝模拟充值会增加本地教学余额，挂号/药费模拟付款不扣真实渠道资金；页面、订单和充值记录对支付宝标注“模拟”。

药费在创建二维码前预留库存。`CREATING/PENDING/UNKNOWN/CLOSING` 的扫码未付处方占用库存，付款后由原 `paid` 处方预留接管，发药时才扣实物库存，避免重复统计。库存维护和药品停用同样受预留保护。

预约支付结果未确认时不会取消预约或释放号源。关闭请求须收到可信关单结果；创建请求超时后立即查询“不存在”不足以释放资源，要等绝对付款期限及补偿窗口结束。创建超时不会覆盖已经发起的关闭意图。

`NEEDS_REVIEW` 表示微信已实付但本地业务存在冲突，页面明确提示“已支付待人工处理，请勿重复支付”，保留支付单和资源保护，不伪报失败或退款。扫码成功后用户资料刷新失败不再遮蔽交易成功。

## 退款边界

参考配置只有 API v2 商户号和密钥，没有退款所需的商户 API 证书。[微信 API v2 退款文档](https://pay.wechatpay.cn/doc/v2/merchant/4011987741) 要求双向证书。本次没有实现或调用真实微信自动原路退款；真实微信订单取消继续要求先处理原渠道退款，不能拿模拟退款流水冒充微信退回。余额订单仍使用原有余额退款流程。

支付宝模拟挂号订单符合取消条件时，已有流程会自动生成 `mock_order_refund`，渠道仍为 `alipay`，并释放号源；因为模拟付款没有扣应用余额，模拟原路退款也不额外增加应用余额。它表示学习流程完成，不表示支付宝真实收到退款。处方药费和充值退款尚未提供独立入口，本次没有扩展这些业务。

2026-11-14 复验：后端 162 项，0 失败、0 错误、1 跳过；客户端最终 54 项全部通过。新增专项检查模拟支付宝挂号 12 次并发取消仅一条退款流水、同键充值仅入账一次、模拟药费库存保障、真实 Native 未确认时禁止切支付宝重复付款、缺少可信模拟付款流水时拒绝模拟退款，以及退款流水 SQL 故障回滚。审查发现并修复了充值确认后切换渠道的异步问题：本次充值固定确认时的渠道，提交中不允许关闭抽屉或切换渠道，两种渠道均有定向回归。证据位于 `.runtime/alipay-compare-20261114/`，最终客户端日志为 `client-final-tests.log`。

## 复验

普通隔离复验不访问真实商户：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File verification/run-verification.ps1 -NativePayments
```

该命令关闭真实通道自动装配，使用合成网关和已有专属 MySQL 验证库。生产 Java 通道验证为单独显式开关，不包含在上述自动回归中：

```powershell
cd backend
mvn "-Dtest=NativeWechatLiveCheckIT" "-Dhealthcare.native.live-check=true" "-Dhealthcare.payment.wechat-native.enabled=false" test
```

后一个命令会创建不展示的短时 1 分验证单并立即关闭，需保持现有私有商户配置可用；不会执行付款。请勿把它误称为完全离线测试。
